# Jay — proud C: Hovory a vyzvánění (Implementation Plan)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development or superpowers:executing-plans to implement this plan task-by-task. Dodržuj vlastnictví souborů (§4) a kontrakty (§3, §5). Nic nenasazuj, nic nepublikuj, na betu ani do produkce nemiř testy. Integrační testy serveru potřebují Docker (Testcontainers). Když lokálně neběží, pusť je v hostovaném CI v public okně (§10) a ve výsledku napiš, že lokálně NEBĚŽELY.

**Goal:** Jay má vyzvánět jako telefon. Příchozí hovor dorazí i při aplikaci na pozadí, po zabití aplikace a na zamčeném telefonu. Volaný slyší vyzvánění a telefon vibruje, volající slyší vyzváněcí tón (ringback), obsazeno a odmítnutí se dají rozlišit. Hovor jde přijmout i přes zámek aplikace, ale chat se tím neodemkne. Hovor přežije výpadek TURN, přepnutí sítě i krátký výpadek SignalR. Uživatel má historii hovorů a vidí zmeškané hovory. Vlna 2 (C2) přidá šifrování signalizace, vyzvánění na všech zařízeních účtu, skupinové hovory (spike SFU), sdílení obrazovky a statistiky kvality.

**Architecture:** Server drží v paměti hubu **čekající nabídku** (pending offer). Kontrakt d): TTL 45 s, jediná instance App Service. Když volaný není připojený, server pošle **hovorový push** přes rozhraní `ICallPushSender`, které implementuje proud N. Po připojení volaného mu nabídku doručí. Na mobilech zobrazuje příchozí hovor nativní vrstva: `flutter_callkit_incoming` (iOS CallKit, Android self-managed Telecom `ConnectionService` + full-screen intent + foreground service `phoneCall|microphone|camera`). VoIP push z PushKitu obslouží vlastní `AppDelegate.swift`. Web a desktop vyzvání v aplikaci (zvuk + notifikace přes N). Signalizace zůstává ve vlně 1 **plaintext** (jako dnes). Šifrování přes existující Double Ratchet session je balíček C2-1. Historie hovorů je **jen lokální** (`CallLog`, drift schema v4 z X0). Firemní hovory dál posílají `call-event` (H1/H2 beze změny).

**Tech Stack:** .NET 10 minimal API + SignalR (hub `MessengerHub`), in-memory `PendingCallStore` + `BackgroundService`, `TimeProvider`. Flutter 3.41.x (CI), `flutter_webrtc` 1.5.2 (beze změny verze), `flutter_callkit_incoming`, `audioplayers`, `wakelock_plus`, `proximity_sensor`, `connectivity_plus`, `window_manager`, Swift (PushKit/CallKit glue), Kotlin (malý kanál pro okno nad zámkem).

**Vychází z:** `docs/gap-analysis-2026-09-29.md` §2, `docs/superpowers/plans/2026-09-29-gap-closure-paralelni.md` (vlastnictví), společné zadání koordinátora (kontrakty a–f), `docs/acceptance/h1-call-metadata.md` (H1/H2), `docs/acceptance/evidence/Q01-09-call-ux.md`.

## 3. Kontrakty proudu C (zmrazit ve vlně 0, `2026-09-29-gap-contracts.md`)

### KC1 — obálka hovorového signálu

Hub metody `CallSignal(target, signalType, payload)` a `BusinessCallSignal(target, signalType, payload, businessGroupId)` se **nemění** (3 resp. 4 argumenty, kvůli regresi `Anonymous_call_signal_still_works_with_exactly_three_arguments`). `payload` je JSON obálka:

```json
{ "v": 1, "callId": "<uuid v4>", "payload": "<sdp | ice | důvod>", "video": true }
```

- `video` je **nové, volitelné** a posílá se jen u `offer`. Starší klient ho ignoruje, protože `_handleSignal` kontroluje jen `v`, `payload` a `callId` (`webrtc_manager.dart:419-424`). Server ho potřebuje pro push, protože SDP v C2-1 zmizí do šifry.
- Server obálku **jen čte** (`CallEnvelope.TryParse`): `v ∈ {1,2}`, `callId` je UUID, `video` je bool (default false). Když se obálka nedá parsovat, jako v existujících testech s `{"sdp":"test"}`, chová se server přesně jako dnes: live relay, nebo `unavailable`, bez pending a bez pushe.

### KC2 — typy signálů (`signalType`)

| Typ | Směr | Payload uvnitř obálky | Nové? | Význam |
| --- | --- | --- | --- | --- |
| `offer` | caller → callee | SDP | — | beze změny, + `video` v obálce |
| `answer` | callee → caller | SDP | — | beze změny |
| `ice-candidate` | oba | `cand\|mid\|idx` | — | beze změny |
| `hangup` | oba | `''` \| `'busy'` \| `'declined'` \| `'cancelled'` | důvody nové | `busy` už existuje. `declined` pošle callee při odmítnutí, `cancelled` caller při zavěšení před přijetím. Starý klient důvod ignoruje |
| `unavailable` | server → caller | echo obálky | — | cíl je offline a **nemá push token** (nebo push selhal) |
| `pushed` | server → caller | echo obálky | **ano** | cíl je offline, push byl odeslán a nabídka čeká (pending) |
| `ringing` | callee → caller | `''` | **ano** | callee nabídku přijal a vyzvání. Server tím potvrdí ring-ack (R-C7), volající přepne na ringback |
| `reoffer` | caller → callee | SDP (ICE restart) | **ano** | renegociace v běžícím hovoru. **Nikdy** se nechová jako `offer`: žádná P1 brána, žádná liveness, žádný pending |
| `reanswer` | callee → caller | SDP | **ano** | odpověď na `reoffer` |
| `restart-request` | callee → caller | `''` | **ano** | callee zjistil `disconnected/failed` nebo změnu sítě. ICE restart dělá vždy jen původní volající (žádný glare) |

Starý klient neznámé typy ignoruje, protože `switch` v `webrtc_manager.dart:461-496` nemá `default`. Firemní hovor posílá **všechny** typy přes `BusinessCallSignal`. Brána H1 platí pro každý typ, liveness auditora jen pro `offer` (`MessengerHub.cs:355`), takže `ringing/reoffer/reanswer/restart-request` běžící hovor nepřeruší.

### KC3 — čekající nabídka (server, v paměti)

- Klíč je `(CalleeDeviceId, CallId)`. Pro dvojici (caller, callee) existuje nejvýš 1 živá nabídka: nová od stejného volajícího nahradí starou a stará dostane `call_cancel`. Na jednoho volaného připadají nejvýš 4 živé nabídky (`Calls:MaxPendingPerCallee`), další `offer` dostane `unavailable`.
- Nabídka drží k tomu až 64 ICE signálů volajícího (`Calls:MaxIcePerCall`) v pořadí, v jakém přišly.
- Stavy: `AwaitingRingAck` (doručeno live, čeká se na `ringing`) → `Ringing`. Offline cesta: `Pending` (push odeslán, nedoručeno) → `Delivered` → `Ringing` → `Answered`. Konec: `Cancelled` (caller), `Declined` (callee), `Expired`.
- TTL je 45 s od vzniku (`Calls:PendingTtlSeconds`). Náhrobek (Cancelled/Declined/Answered/Expired) se drží dalších 120 s (`Calls:TombstoneSeconds`), aby `ClaimPendingCall` uměl říct „zrušeno“.
- Limit pushů je 6 hovorových pushů za minutu na volajícího (`Calls:MaxCallPushesPerCallerPerMinute`). Nad limitem server odpoví `unavailable`. Je to ochrana proti „ring bombingu“.
- Úklid dělá `PendingCallSweeper` (BackgroundService, tick 1 s): řeší vypršené ring-acky a jednou za 10 s maže prošlé záznamy.
- Stejná mez jako `ChannelPushThrottle`: data jsou jen v paměti a správná jen při jedné instanci (CLAUDE.md rozhodnutí 6). Restart API zahodí čekající hovory, volající pak skončí na svém timeoutu.

### KC4 — hovorový push (implementuje N, volá C)

Rozhraní, které X0 zmrazí jako stub (`src/server/CallType.Api/Services/ICallPushSender.cs`):

```csharp
public enum CallPushResult { NoToken, NotConfigured, Sent, Failed }

public sealed record CallPush(Guid CallId, bool Video, string DeclineToken, DateTimeOffset ExpiresAt);

public interface ICallPushSender
{
    /// Wakes the callee's device for an incoming call. Returns Sent only when a
    /// provider accepted a push that can present a ringing UI (APNs VoIP or
    /// FCM high-priority data / webpush). Never throws.
    Task<CallPushResult> SendCallPushAsync(Guid calleeDeviceId, CallPush push, CancellationToken ct);

    /// Best-effort: stops a ringing native UI after the caller hung up before
    /// the callee connected. Never throws.
    Task SendCallCancelPushAsync(Guid calleeDeviceId, Guid callId, CancellationToken ct);
}
```

Směrování (N): `Device.VoipPushToken != null` → APNs VoIP, jinak `PushPlatform == "fcm"` → FCM, jinak `NoToken`. Tvary (**žádná identita volajícího**, kontrakt d):

- **FCM** (Android, web), `message.data` jsou vždy stringy:
  - `{"type":"call","callId":"<uuid>","video":"true|false","declineToken":"<base64url>","expiresAt":"<unix ms>"}`
  - Android: `android.priority: "HIGH"`, `android.ttl: "45s"`. Webpush: hlavičky `Urgency: high`, `TTL: 45`.
  - Zrušení: `{"type":"call_cancel","callId":"<uuid>"}`, stejná priorita a TTL.
- **APNs VoIP** (iOS): hlavičky `apns-push-type: voip`, `apns-topic: cz.zcloud.jay.voip`, `apns-priority: 10`, `apns-expiration: <expiresAt v unix s>`.
  - Tělo: `{"aps":{},"type":"call","callId":"<uuid>","video":false,"declineToken":"<base64url>","expiresAt":<unix ms>}`.

Pravidlo iOS 13+: každý VoIP push = `reportNewIncomingCall`, jinak systém aplikaci zabije a po opakování jí přestane doručovat VoIP pushe.

### KC6 — lokální historie hovorů (`CallLog`, drift v4 z X0) a `CallRecord`

- `WebRTCManager.callRecords` (nový broadcast stream) emituje po **každém** hovoru (i anonymním) jeden `CallRecord`. `callReports` (H2) zůstává beze změny a emituje jen pro firemní hovor.
- `CallRecord.outcome` (lokální, **není** to whitelist H1): `completed | missed | declined | busy | unavailable | noAnswer | cancelled | failed`.
  - Odchozí: `completed / noAnswer / declined / busy / unavailable / cancelled / failed`.
  - Příchozí: `completed / missed` (vypršel, nebo volající zrušil dřív, než jsem přijal) `/ declined / failed`.
- Mapování na H1 `CallReport.outcome` (nesmí se měnit whitelist): `busy`, `declined`, `cancelled` → `rejected`; `noAnswer`, `missed` → `missed`; `unavailable` → `unavailable`; `failed` → `failed`. Nové chyby `businessConversationRequired` a `callNoLongerAvailable` **nevytváří** `CallReport` (hovor se nekonal), stejně jako dnes `auditorUnavailable`.

### Sekvence (normativní pro C02/C06/C07)

**A — callee online, aplikace v popředí:** offer → hub relay live + `AwaitingRingAck` → callee `WebRTCManager` ringing → pošle `ringing` → hub označí `Ringing` a relay na volajícího → ringback. Mobil: `CallKitBridge` ukáže nativní UI se skutečným jménem (R-C3).

**B — iOS, aplikace zabitá nebo zamčený telefon:**
1. Offer, callee offline → `SendCallPushAsync` = `Sent` → `Pending` + volajícímu `pushed`.
2. PushKit → `AppDelegate` **okamžitě** `showCallkitIncoming(nameCaller: "Jay", id: callId, type: video?1:0, extra: {callId, declineToken, expiresAt, apiBase})`.
3. iOS spustí proces, Flutter `main()` → `signalRClient.connect()` → `OnConnectedAsync` doručí pending offer + ICE → `WebRTCManager` ringing → `ringing` → volající slyší ringback.
4. `CallKitBridge` aktualizuje jméno volajícího (volitelné, [OVĚŘIT] viz C06 krok 7).
5. Přijetí v CallKitu → `acceptCall()` → `didActivate audioSession` → `RTCAudioSession.audioSessionDidActivate`.
6. Přijal uživatel dřív, než dorazila nabídka? → `prepareForIncoming(callId, autoAccept: true)` + `ClaimPendingCall(callId)`. Stav `cancelled/expired/unknown` → `endCall(callId)` v CallKitu + `CallRecord missed` / `CallError.callNoLongerAvailable`.

**C — Android, aplikace zabitá:**
1. FCM high-priority data → N background isolate → `handleCallPush` → `FlutterCallkitIncoming.showCallkitIncoming` (FSI, Telecom, FGS).
2. Přijetí → plugin spustí `MainActivity` → `main()` → connect → pending offer → `CallKitBridge` vidí `isAccepted` pro `callId` → auto-accept. `CallWindowChannel.setShowWhenLocked(true)` po dobu hovoru.
3. Odmítnutí → `FlutterCallkitIncoming.onBackgroundMessage` handler (Dart, background) → `POST /calls/{callId}/decline` s `declineToken` (bez JWT).

**D — web, zavřená záložka:** FCM webpush → service worker (N) ukáže notifikaci „Jay — příchozí hovor“ (`requireInteraction: true`) → klik → otevře/fokusuje aplikaci → connect → pending offer → vyzvánění v aplikaci.

**E — mrtvý socket (zařízení „online“, ale uspané):** live offer → do 5 s žádný `ringing` → sweeper pošle push. Při `Sent` jde volajícímu `pushed` a stav se změní na `Pending` (nedoručeno), takže se offer + ICE doručí znovu po připojení. Když push není (`NoToken`), nic dalšího se nepošle: callee může být starý klient, který `ringing` neposílá.

**F — volající zavěsí před přijetím:** `hangup 'cancelled'` → hub: nabídka ve stavu `Pending/Delivered/AwaitingRingAck` → `Cancelled`. Pokud callee nebyl připojený (`Pending`), jde `SendCallCancelPushAsync`. Pokud je připojený, relayuje se `hangup` jako dnes.

## 8. C2 — vlna 2

### C2-1 — Šifrování signalizace přes Double Ratchet (L)

**Problém:** SDP a ICE jdou přes hub v plaintextu (`webrtc_manager.dart:366-371`). Server vidí IP adresy obou stran a mohl by podvrhnout DTLS fingerprint v SDP, tedy MITM médií.

**Návrh:**

1. **Offer, answer, reoffer, reanswer** jdou šifrované existující session `SessionManager.encryptMessage(peer, plaintext)` (`calltype_core/lib/crypto/session_manager.dart:200`). Plaintext je JSON `{"sdp": "...", "ck": "<base64 32 B>"}`, `ck` (per-call klíč) jen v offeru.
2. **ICE, hangup důvod, ringing a restart-request** jdou šifrované per-call klíčem `ck` (AES-256-GCM, 12B nonce náhodný):
   - AAD = `utf8("CallType-CallSignal-v1|" + callId + "|" + signalType + "|" + senderDeviceId)`. Nový doménový separátor, stávající `CallType-*` se nemění (CLAUDE.md).
   - PROČ: DR krok = zápis session do DB. ICE je 10–30 zpráv za hovor a přicházejí mimo pořadí. Per-call klíč nepotřebuje stav ani pořadí.
3. **Obálka v2:** `{v:2, callId, video?, e:"dr"|"ck", n?:"<nonce b64>", payload:"<b64 ciphertext>"}`.
   - `signalType`, `callId`, `video` a `businessGroupId` zůstávají **venku**: hub podle nich dělá bránu H1, P1, pending a push.
   - Server tak dál vidí metadata (kdo, komu, kdy, audio/video), ne SDP ani IP kandidáty. IP vidí jen TURN/STUN.
4. **Pořadí:** DR operace běží přes `MessageProcessingQueue.forDatabase(db)` (`lib/features/chat/message_inbox_service.dart:12-23`), stejně jako `CallEventSender`, aby se hovor nepromíchal s ratchet updaty zpráv.
   - Chybí session → `initiateSession(getKeyBundle)` (vzor `call_event_sender.dart:157-164`). Offer je pak pre-key zpráva.
   - Dešifrování offeru selže → callee pošle `hangup` s důvodem `decrypt_failed` (plaintext kód) → volající zobrazí chybu a navrhne obnovu session (S).
5. **Výkon** (měřit v rámci C2-1): 2–4 DR operace na hovor. Cíl je < 50 ms na webu (drift worker) a < 10 ms nativně. ICE se šifruje v paměti bez DB.
6. **Kompatibilita a downgrade:**
   - Klient ohlásí `caps: ["call-sig-v2"]` ve zprávě `profile` (§5.7) a uloží si caps kontaktu (G sloupec nebo `AppSettings` klíč `caps:<deviceId>`).
   - Volající posílá v2 jen kontaktu s capem.
   - Callee, který od kontaktu **už viděl** v2, **odmítne** v1 offer od tohoto kontaktu. Jinak by server mohl podvrhnout plaintext offer, protože `senderId` dosazuje server.
   - Po přechodném období (vlastník) v1 úplně vypnout.
7. **Business:** hovorová signalizace nikdy nejde auditorovi, protože to není skupinový fan-out. Brána H1 (`businessGroupId` venku) se nemění, `CallReport` a `call-event` se nemění. Regresní sada §9 musí být zelená.
8. **Docs:** S aktualizuje `docs/security/crypto-baseline.md` (nový separátor, AES-GCM per-call klíč, co server vidí).

**Testy:**
- unit: v2 roundtrip přes dvě `SessionManager` instance (vzor `call_event_sender_test.dart`)
- ICE s per-call klíčem
- pozměněný AAD → odmítnuto
- v1 od kontaktu s v2 capem → odmítnuto
- server stále parsuje `callId/video` (C02 testy s v2 obálkou)

### C2-2 — Vyzvánění na všech zařízeních účtu, „přijato jinde“ (M, závisí na D)

- **Klient:** volající si přes API proudu D zjistí zařízení účtu volaného a pošle **stejný `callId`** všem. U v2 je každý offer šifrovaný zvlášť.
- **Hub:** `ActiveCallRegistry` (vedle `PendingCallStore`) hlídá `callId → answeredBy`:
  - První `answer` vyhrává. Každý další `answer` dostane zpět `hangup 'answered-elsewhere'`.
  - Ostatní zařízení volaného dostanou `hangup 'answered-elsewhere'`.
  - `declined` z jednoho zařízení ukončí vyzvánění na všech (jako WhatsApp).
  - Pending + push pro každé offline zařízení zvlášť.
- **Business:** každé zařízení musí být členem `businessGroupId`, jinak ho brána H1 odmítne. Vyzvání pak jen zapsaná zařízení.
- **Klient:** `CallError.answeredElsewhere` → tichý konec a `CallLog` outcome `answeredElsewhere` (rozšířit lokální set, H1 whitelist beze změny).

### C2-3 — Skupinové hovory: spike (M, výstup `spikes/group-calls/REPORT.md`, nic do `src/`)

| Varianta | Infrastruktura | E2EE | Platformy | Poznámka |
| --- | --- | --- | --- | --- |
| **Mesh do 4 osob** | žádná (hub + TURN) | ano (DTLS-SRTP peer-to-peer, s C2-1 i signalizace) | vše, co umí `flutter_webrtc` | uplink = (n−1) × stream. Video pro 4 osoby ≈ 3 × 500 kbps. Nejmenší změna |
| **LiveKit self-hosted** | samostatný kontejner/VM (Go SFU + TURN) mimo App Service | insertable streams (`FrameCryptor`) + klíč rozdaný přes DR sessions | `livekit_client` 2.13 **[OVĚŘIT]** web/desktop | nový provozní prvek (O), škáluje |
| **Cloudflare Calls (Realtime SFU)** | managed, platba za egress | insertable streams jako výše | stejné jako `flutter_webrtc` | žádný server, ale data přes Cloudflare |

Kritéria spiku:
- build a běh 3–4 účastníků na webu, Androidu, iOS a Windows
- CPU a baterie telefonu při 4× video
- E2EE a rotace klíče při odchodu člena
- doba připojení
- chování přes TURN
- co uvidí auditor: **jen metadata**, každý účastník posílá `call-event`; auditor není mediální účastník, jinak by šlo o nahrávání (business plán §8a bod 4)

Doporučená výchozí hypotéza: mesh ≤ 4 pro MVP, SFU až podle poptávky. **[ROZHODNUTÍ]** vlastníka po spiku.

### C2-4 — Sdílení obrazovky (M)

- Web a desktop: `navigator.mediaDevices.getDisplayMedia` + `replaceTrack` na video senderu.
- Android: MediaProjection. Android 14 vyžaduje FGS typ `mediaProjection` + `FOREGROUND_SERVICE_MEDIA_PROJECTION` a souhlas při každém sdílení (X0 vlny 2).
- iOS: ReplayKit Broadcast Upload Extension je nový target + App Group (P). Mimo C2-4, samostatné zadání.

### C2-5 — Statistiky kvality (S)

- Každé 2 s `peer.getStats()` → RTT (`candidate-pair.currentRoundTripTime`), ztrátovost (`inbound-rtp packetsLost / (packetsLost + packetsReceived)`), jitter, `availableOutgoingBitrate`.
- Výsledek `CallQuality {good, fair, poor}` s hysterezí 3 vzorků → ikona v `CallScreen`.
- Při `poor` u videa `RTCRtpSender.setParameters` s `maxBitrate` 300 kbps a 15 fps.
- Diagnostický panel bez IP a SDP (stejná zásada jako `getSelectedCandidateSummary`, `webrtc_manager.dart:499-524`).
