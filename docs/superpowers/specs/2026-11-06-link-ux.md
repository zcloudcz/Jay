# Link UX - linking web / desktop to the phone (stage A)

Status: implemented on `feat/link-ux` (app only, no server change). Builds on
spec 1, `2026-10-13-multi-device-sync-design.md`; manual acceptance in
`docs/acceptance/multi-device.md` (M-01..M-03, M-24..M-28).

## Problem

Owner feedback on the beta web: "not user friendly".

1. "Get started" on the web registered a brand new identity at once. Linking
   to the phone was a secondary button shown only afterwards, so people
   started as a second, empty user by accident.
2. A device with contacts or chats refused to link ("only a device without
   contacts and chats"). The only way out was a fresh browser profile or a
   private window.
3. Signing in with the e-mail account on the web showed no conversations and
   nothing said why. That is by design (the account holds backups only), but
   it looked broken.
4. On the phone, linking was three levels deep: Settings > Linked devices >
   Link a device.

## The four changes

| # | Where | What the user sees |
|---|---|---|
| A1 | Onboarding on web and desktop (`isLinkFirstPlatform`) | "Use Jay from your phone", the link QR code and three steps (open Jay on the phone, tap "Link web / computer", scan). Below it a smaller "I don't have Jay on a phone, start here", which shows the standalone identity as before. Phones keep "Get started". |
| A2 | Phone: chat list app bar (scanner icon) and the first row of Settings | "Link web / computer" opens the existing scanner and the primary's link dialog directly. Hidden on a companion (only the primary signs the list) and where nothing can scan (Windows / Linux, same rule as the contact scanner). At 5 companions it says the limit instead. |
| A3 | Settings > Linked devices on a device with data, and the "not empty" state of the link screen | "Disconnect this device and link it with your phone": a dialog says the chats and contacts on this device are deleted and its identity is lost, offers "Back up first" (opens Settings > Backup), and needs an explicit "Delete and link". Then the device is emptied and shows the link code. A companion, or a primary with companions, is refused with an explanation, before anything is asked. |
| A4 | Account screen after a successful login on web / desktop | When the device has no conversations (and is not a companion): "Where are my chats?" explains that chats are end-to-end encrypted and live only on the user's devices, that the account is for backups, and offers "Link with my phone" (the link screen). What login does is unchanged. |

### Decisions

- **Silent registration on the link path.** The link code needs a device id
  and keys, so the link-first screen registers the device in the background
  before showing the code. Its handle is never shown on that path. A device
  that never gets linked stays registered, as it did before (accepted).
  "Start here" reuses that registration instead of creating a second device.
- **`ct_link_pending` marker (secure storage).** Set when the link path starts
  or after a disconnect, cleared when the link finishes or the user picks
  "start here". While it is set, the router sends every route to
  `/onboarding?link=1`. Without it a page reload during linking would land in
  an empty chat list as an unintended new identity, the original problem. If
  the device became a companion but the marker survived (closed tab), the
  router drops it.
- **Reset for linking keeps keys and the device id**
  (`DeviceService.resetForLinking`). It deletes what the companion wipe
  deletes (messages, conversations, contacts, outbox / control state, the
  companion markers) plus the Signal sessions and the pending "vanished
  companions" prompt. Sessions go because the identity is given up: ratchets
  with the old contacts must not keep decrypting their messages on a device
  that then reads the phone's conversations. Keys and registration stay
  because the link code carries this device id, and recreating an identity
  in-process (SignalR, WebRTC and the directory hold the id) is far riskier
  than reusing the empty-device state the companion wipe already produces and
  the link flow already accepts. Stored device lists stay, for the rollback
  reason in spec 1 ("Removing a device").
- **Refusal for a primary with companions**: its signed list would be
  orphaned and the companions could no longer be managed. A companion is
  refused too (relinking a companion to another phone is out of scope).
- **A4 goes to `/settings/devices/link`**, the plain link screen, not the
  link-first onboarding: the user just signed in on a device that may already
  be in use, so nothing is marked pending and nothing is deleted.

## Security model: unchanged

- Access to conversations only through the phone scanning this device's QR
  code, fingerprint check, LinkOffer / LinkConsent and the signed list, exactly
  as in spec 1. No server endpoint, hub method or payload changed.
- The server still cannot add a device. The account login still only links
  the device to the account for backups.
- The new reset deletes only local data, after an explicit confirmation on the
  device itself. Nothing remote can trigger it.

## Limits

- The old identity's server-side group memberships are not left (there is no
  client "leave group" call yet). With the sessions deleted, messages from old
  contacts and groups normally cannot be decrypted on the reset device; a
  sender that starts a NEW session (pre-key message) could still appear there
  as a conversation. Accepted for stage A.
- Out of scope (stage B): transferring history, contacts and groups to the
  newly linked device; read-state sync.
