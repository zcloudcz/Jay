# Bot factory: one-command bots, a thin LLM bridge, and "New bot" in the app

Status: approved direction by Martin 2026-11-09 (Discord): "script a obdoba BotFather bude správná volba, ideálně když BotFather rovnou script i nabídne. Za JayBotem může být Hermes, ale chtěl bych mít i jen Claude subscription nebo ChatGPT, tenká vrstva obalující OpenAI a Anthropic. Aby uživatel, který chce bota do Jay, nemusel instalovat celý Hermes."

## Why
Creating a bot today means building a Dart package or a Docker image, generating a key, writing ten env variables and reading the handle from a log. Only an admin can do that. Target: a user taps "New bot" in Jay, copies ONE command, runs it on any machine, and a minute later the bot writes to him in Jay.

## Constraints (do not break)
- E2E: a bot is an ordinary device; its private keys are created and stay on the machine that runs it. The Jay server never holds bot keys or plaintext. Therefore the bot cannot be "hosted by the app"; the app only prepares the command.
- Fail-closed access: a bot answers only its owner(s) (`ALLOWED_HANDLES`).
- Claude/ChatGPT subscriptions: Anthropic does not allow third-party apps to collect, store or route Claude.ai (Pro/Max) credentials; developer products must use API keys (code.claude.com/docs/en/legal-and-compliance). So Jay never asks for, stores or forwards subscription logins or tokens. The supported "subscription" path is: the owner installs the official CLI himself and signs in through the vendor's own flow (`claude` for Claude Code, `codex` for Codex CLI with ChatGPT login); the bridge only runs that local CLI as a subprocess for the owner's own messages (personal, individual use). Documented as such, with the vendor terms linked.

## Decisions

| # | Decision |
|---|---|
| B1 | New package `src/bots/llm_bridge` (Dart, on `calltype_bot`, structured like `a2a_bridge`): a chat bot with conversation memory per chat, no tools. Providers via `LLM_PROVIDER`: `anthropic` (Messages API, `ANTHROPIC_API_KEY`, default model `claude-sonnet-5-5` with `output_config.effort` `low`, overridable `LLM_MODEL` / `LLM_EFFORT`), `openai` (Chat Completions, `OPENAI_API_KEY`, `OPENAI_BASE_URL` so Azure OpenAI, OpenRouter, Ollama, LM Studio and any OpenAI-compatible endpoint work; default `gpt-6.1-sol` with `reasoning_effort` `low` on api.openai.com only, other endpoints require `LLM_MODEL` and get no effort field; the key is optional off api.openai.com), `claude-cli` (runs `claude -p --output-format json --system-prompt-file <f> --tools "" --no-session-persistence --disable-slash-commands [--model m]` with the conversation on stdin, in an empty work dir; uses the owner's own Claude Code login; never `--bare`, which ignores that login), `codex-cli` (runs `codex exec --skip-git-repo-check --ephemeral --sandbox read-only --color never [-m m] -` with the system prompt + conversation on stdin; owner's own ChatGPT login). `LLM_SYSTEM_PROMPT` (default: short friendly assistant prompt that answers in the user's language), `LLM_HISTORY_MESSAGES` (default 20), `LLM_MAX_TOKENS` (default 8192: thinking counts against it on current Claude models). |
| B1a | Why these defaults (vendor docs checked 2026-11-09, the first draft named `claude-sonnet-4-5`, which is no longer current): Claude Sonnet 5.5 is the "speed and intelligence" tier and Anthropic recommends `low`/`medium` effort for chat (Sonnet 5.5 defaults to `high`). GPT-6.1 Sol is OpenAI's recommended balance of intelligence and cost and lists Chat Completions as supported. Chat Completions instead of the Responses API because the compatible servers implement only Chat Completions and the bot needs no tools. |
| B2 | Behaviour reuses what `hermes_bridge` already does where it is generic: 1:1 and group addressing (@mention / reply), typing indicator, chunking of long answers, "Working on it..." progress edit after N s, `BOT_COMMANDS` (`/new` resets the memory of this chat, `/help`), streaming where the provider supports it (edit the progress message), reactions ignored. Extract shared pieces into `calltype_bot` only if it is small and safe; otherwise copy with a comment. Voice/STT/TTS out of scope. |
| B3 | History is stored locally, per conversation, capped by B1, in `<BOT_STORE_PATH>.llm`: a separate file encrypted with `BOT_STORE_KEY` in the identity store's AES-256-GCM format. (Changed from "`backupState` rows in the bot store DB": that SQLite file is plaintext on disk, and the identity store file is owned and rewritten by the runtime, so a second writer would race it.) Never sent anywhere except the chosen provider. Delete the file to forget every chat. |
| B4 | First start: after connecting, the bot sends its owner(s) a greeting 1:1 ("Ahoj, jsem <name>. Napiš mi." plus the same in English on a second line) once (marker in the B3 store, written only after a successful send, so a failed greeting is retried on the next start), so the bot appears in the owner's chat list without typing a handle. The app already adds a contact when the owner replies (contacts-from-replies). Also print handle + `ct://` invite to stdout as today. |
| B5 | Distribution without Dart: GitHub Actions workflow `llm-bridge-release.yml` (manual, SHA-pinned) builds `dart build cli` bundles of `llm_bridge` AND `hermes_bridge` (the latter for `--provider hermes`) for linux-x64, linux-arm64 (`ubuntu-24.04-arm`, free for public repos), macos-arm64, windows-x64, smoke-tests each binary (exit 78 on missing config), and publishes them with a `SHA256SUMS` file on a rolling tag `llm-bridge-latest` (stable download URLs `.../releases/download/llm-bridge-latest/jay-<llm|hermes>-bridge-<os>-<arch>.zip`; the scripts verify the checksum). The release is a prerelease and never "latest", because `/releases/latest/download/Jay-windows-x64.zip` must keep pointing at the Windows app. Plus a Docker image `ghcr.io/zcloudcz/jay-llm-bridge` (`llm-bridge-image.yml`) like the other bridges. The repo is public, so assets are public. No macOS x64 bundle (Intel Macs: `--docker`). |
| B6 | `infra/bots/jay-new-bot.sh` (Linux/macOS) and `infra/bots/jay-new-bot.ps1` (Windows): ONE command. Args: `--name`, `--owner CT-XXXX-XXXX[,..]`, `--provider anthropic|openai|claude-cli|codex-cli|hermes`, `--api https://...` (default beta API), optional `--model`, `--prompt`. It downloads the right bundle (B5) to `~/.jay-bots/<name>/`, generates `BOT_STORE_KEY` (32 random bytes, never printed), asks for the provider API key with a hidden prompt (or reads it from env; never as an argument, so it does not land in shell history), writes a 600 env file, installs a user service (systemd --user on Linux with linger hint, launchd agent on macOS, Scheduled Task at logon on Windows), starts it, waits for the handle line and prints: handle, invite, "check Jay, the bot just wrote to you". `--provider hermes` sets up `hermes_bridge` instead (needs `HERMES_URL`/`HERMES_API_KEY`). Idempotent: rerun with the same name updates the binary and keeps the identity; `--remove` stops and deletes the service (asks before deleting the store, which deletes the identity). Hosted at `https://jay.zcloud.cz/bots/new-bot.sh` and `.ps1` via the web build (symlinks `web/bots/` -> `infra/bots/`, `/bots/*` excluded from `navigationFallback`, served as `text/plain; charset=utf-8`, `Cache-Control: no-cache`; `deploy.yml` checks the files are in `build/web/bots/`) so the command is `curl -fsSL https://jay.zcloud.cz/bots/new-bot.sh | bash -s -- --name ... --owner ...`. |
| B6a | As built: Docker is the `--docker` flag of the same `.sh` script (container `jay-bot-<slug>`, named volume, `--restart unless-stopped`, image from B5; API providers and hermes only, the CLI providers are refused because they need the owner's signed-in CLI on the host). More options: `--base-url` (openai-compatible endpoint), `--hermes-url`, `--yes` (with `--remove`), `--dry-run` (plus test-only `--os`/`--arch`). The folder/service name is a slug of `--name` (accents folded, `[a-z0-9-]`, max 32), so the name must contain a Latin letter or digit. Settings: `bot.env` (POSIX single-quoted, 600) sourced by a generated `run.sh`, which every service manager starts; Windows: `bot.env.json` with an ACL for the current user only and a `run.ps1` restart loop. Exit 78 (bad settings) is never restarted. On a rerun the store key and the provider key are taken from the existing settings, optional settings are kept unless given again, and the running bot is stopped only after the new bundle passed the checksum. The Windows one-liner is `& ([scriptblock]::Create((irm https://jay.zcloud.cz/bots/new-bot.ps1))) -Name ... -Owner ... -Provider ... -Api ...`. `hermes_bridge` has no greeting (B4 is llm_bridge only), so for `hermes` the script tells the owner to add the bot by handle. Tests: `infra/bots/test-scripts.sh` (CI job `bot-scripts`). |
| B6b | As built / fix (`fix/bot-cli-path`): a service starts with a minimal PATH, and an npm-installed `codex`/`claude` is a `#!/usr/bin/env node` script whose node often lives in a non-standard dir (nvm, a tarball), so a codex-cli bot answered every message with "Codex exited with code 127: env: 'node': No such file or directory ... (is it signed in?)". Now the scripts read the CLI's shebang (symlinks followed; `env X` and `env -S X ...` resolved with the installing user's PATH, an absolute interpreter used as is) and build the service PATH `<interpreter dir as found>:<its real dir, if a symlink>:<CLI dir>:/usr/local/bin:/usr/bin:/bin` (deduplicated), written into `run.sh` (all service managers) and the launchd plist (`EnvironmentVariables`). Windows: an npm `.cmd` shim (or a `#!` script) needs `node`; `run.ps1` puts `<node.exe dir>;<CLI dir>` in front of the task's PATH. Before anything is written or started, the CLI is started once with exactly that PATH (`env -i HOME=... PATH=<service PATH> <cli> --version`; Windows: machine + user PATH behind the prefix); a missing interpreter or a failed start stops the install with a message naming the interpreter and the PATH. `--dry-run` prints the service PATH and the check command; `--check-only` runs only the check and changes nothing; `CLAUDE_BIN`/`CODEX_BIN` in the environment select a specific CLI. `--docker` is unaffected. llm_bridge: exit 127/126 or a shell/`env`/cmd "not found" text maps to "The <CLI> or its interpreter (node) cannot be started; check the bot service PATH (rerun the setup command)."; the "is it signed in?" hint only for known login failures (claude: "Not logged in", "/login", "Invalid API key", "OAuth token expired", 401; codex: "401 Unauthorized", "Missing bearer", "Not logged in", "codex login", "refresh token", "token expired"); anything else is neutral "<CLI> failed with exit code N: <excerpt>". Existing bots get the PATH by rerunning their setup command after the release. |
| B7 | App: Settings -> "Bots" -> "New bot" (and the same entry in the new-chat menu). Wizard: name, what is behind it (Claude API key, OpenAI/compatible API key, my Claude subscription via Claude Code, my ChatGPT subscription via Codex, Hermes agent), OS (preselected from the current platform, Linux/macOS/Windows/Docker). Result screen: the exact one-line command with `--name`, `--owner <my handle>` and `--api <current API base URL>` filled in, Copy button, short steps ("run it on a computer that stays on; the bot will write to you"), and for subscription providers one line on what the user installs first and that it is for personal use. No server call, no key ever entered in the app. All strings in 19 ARB files. Web included (that is where copy/paste of a command is most natural). |
| B7a | As built: Settings -> "Bots" (intro: what a bot is, keys stay on the bot's computer) -> "New bot"; the same wizard opens from a robot icon in the app bar of the contacts screen, which is where "New chat" leads (`/settings/bots/new`). The owner handle is the identity's handle (on a companion device the linked primary's, like the identity screen). The target is preselected from the platform (in a browser: the browser's OS); on Android/iOS it is Linux, because a phone cannot host a bot. Docker disables the two subscription choices. The result shows the command, Copy, numbered steps (terminal or PowerShell; "paste your API key there" only for key providers; "the bot writes to you within a minute"), the install note for the subscription and Hermes choices, and the update/remove hint. Script host is fixed to `https://jay.zcloud.cz/bots/`; `--api` is the app's own `API_BASE_URL`. Quoting: POSIX single quotes for bash, doubled single quotes for PowerShell (no `$` expansion); a test feeds hostile names through a real bash. |
| B8 | Server: no change in this step. (A server-side "my bots" list with remote revoke is a later step; it needs a claim protocol and is out of scope.) |
| B9 | This machine: after merge, the owner gets a second bot here via the script (done by the ops agent, not part of this branch). |

## Tests
- llm_bridge: unit tests with a fake provider HTTP server for anthropic and openai (request shape incl. system prompt and history, streaming parse, error -> apology message, 429 retry once), CLI providers with a fake executable on PATH (args, timeout, non-zero exit), history cap and `/new`, greeting sent once, owner-only (non-owner dropped before decrypt, like a2a_bridge tests). `dart analyze` clean.
- Script: `shellcheck`; a test mode `--dry-run` that prints the actions; a CI job (or local test) runs `--dry-run` for each provider/OS combination. PowerShell: `Invoke-ScriptAnalyzer` if available in CI, else syntax parse.
- App: widget tests for the wizard (command contains name/owner/api/provider, quoting safe for names with spaces and quotes, no key field anywhere), l10n guard, `flutter analyze`.
- Web: `/bots/new-bot.sh` is served as text (staticwebapp config exclusion) - assert in a config test or document in acceptance.

## Limits
- The bot runs only while the user's machine runs it.
- Subscription providers are personal use and depend on the vendor CLI staying available; API keys are the robust path.
