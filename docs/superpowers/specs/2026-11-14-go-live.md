# Go-live: production release in Google Play and the App Store

Status: contract for branch `feat/go-live` (from `origin/master` 7dd4dcf).
Owner request 2026-11-14: "Chci pro iOS i Android uz ostre verze".

This spec covers what the APP, the SERVER and the WEB must contain before the
first production release in Google Play and the App Store (checklist:
"Go-live gates" in the jay-development skill). Store console work (listings,
Data safety form, App Privacy labels, screenshots, trader status, export
compliance answer) is the owner's and is only prepared here as drafts in
`docs/store/listing.md`.

Out of scope on purpose: `ITSAppUsesNonExemptEncryption` in `Info.plist`
(the export answer is the owner's legal declaration, still pending).

## Decisions

| # | Decision | Why |
|---|----------|-----|
| D1 | A block is per IDENTITY (primary device id), on both sides. Blocking a companion's id blocks its identity. | Conversations are keyed by identity; a blocked person must not get through from their laptop. |
| D2 | The server enforces a block by silently dropping the blocked identity's copies to the blocker's devices on EVERY send path (1:1, group, fan-out, silent variants), its call signals and its typing indicators. The sender gets the same ack as for a delivered message. | Same "no oracle" rule as the bot inbound filter: the sender must not learn that they are blocked. Groups are included because otherwise a blocked person could create a group with the victim and keep writing. |
| D3 | Blocking also deletes the not yet delivered queued messages from the blocked identity's devices to the blocker's devices. | A block must stop what is already waiting, not only new sends. |
| D4 | Group membership is not changed by a block; the blocker can still leave or remove. Control messages (topic, reactions) of the blocked person are dropped like everything else. | Removing a member is the group's decision, not one member's. |
| D5 | The app keeps a local cache of the block list in the drift `backup_state` table (`block:<identityId>` keys), refreshed from `GET /blocks` on every hub connect. A blocked identity's 1:1 chat is hidden from the chat list. | Skill rule 9 (no schema bump). The server list is the truth; the cache only keeps the UI right offline. |
| D6 | User reports reuse the channel report categories (`illegal`, `terms`, `spam`), the good-faith rule for `illegal` and the optional contact e-mail. | One report dialog and one set of translated labels for channels and users. |
| D7 | Evidence: the server cannot read E2E content, so the REPORTER's app may attach the decrypted text of selected messages. The user ticks this explicitly and is told that these texts go to the operator readable. Default: on for a report started from a message, off otherwise. | Apple 1.2 asks for a way to report objectionable content; the operator needs the content to act on it. |
| D8 | A user report never exposes the reporter to the reported user; the operator API does not return the reporter's device id either (same rule as channel reports). | Reporter safety. |
| D9 | User reports are deleted after `Moderation:UserReportRetentionDays` (default 180) days by `MessageCleanupService`. | Evidence holds message text; it must not live forever. Retention is stated in the privacy policy. |
| D10 | "Delete account" in the app deletes the whole identity: the account (if registered), this device and, on a primary, every companion in its device list (`DELETE /devices/{id}?includeCompanions=true`). On a companion it deletes the account link and this device only, and says that the identity lives on the primary. | Apple 5.1.1(v): deleting in the app must delete the account, not just log out. A companion cannot delete its primary. |
| D11 | Deleting a registered account needs the passphrase again (`DELETE /accounts/{id}` requires the auth key, unchanged), plus a typed confirmation: the user's own handle. With the app lock on, a PIN or biometric check runs first. | Irreversible action; a stolen unlocked phone must not delete the account in two taps. Typing the handle needs no translation. |
| D12 | After a successful server deletion the app wipes local data in-process (drift tables, secure storage except the database key, media files, in-memory caches), disconnects, and goes to onboarding. | Returning to onboarding without an app restart; the database key stays because the open encrypted database file is reused. |
| D13 | Export: a registered device exports `GET /accounts/{id}/export`; an anonymous device exports the new `GET /devices/{id}/export`. Both include group memberships, mutes, blocks and user reports filed. The app saves the JSON with the share sheet on iOS and Android and as a download / save dialog on web and desktop. | GDPR access right applies to anonymous identities too; the old export lacked group memberships. |
| D14 | Legal pages are static HTML in `src/client/calltype/web/legal/` (served by the app's Static Web App at `https://jay.zcloud.cz/legal/...`), cs + en, same style as `channels-*.html`, operator details in a footer. The app picks cs for a Czech UI, else en. | One host for app and legal texts; no SPA fallback for `/legal/*` already. |
| D15 | `/.well-known/security.txt` is served as a static file of the Static Web App (same contact as the API's) and `/.well-known/*` is excluded from `navigationFallback`. | Today the web host answers it with the Flutter index.html. |
| D16 | The privacy policy names the real processors from the running configuration: Microsoft Azure (West Europe: API on App Service, blob storage, web on Static Web Apps), Hostinger (PostgreSQL database on a VPS; the page names no data centre location until the owner confirms it), Cloudflare (TURN relay), Google FCM and Apple APNs (content-free push), and Mozilla/Google/Apple/Microsoft web push services for browsers. | The database is NOT in Azure (owner brief said so); the policy must say what is true. |

## Server

| # | Rule |
|---|------|
| S1 | New entity `UserBlock` (table `UserBlocks`): `Id` (long), `BlockerPrimaryId` (Guid, FK Device, cascade), `BlockedPrimaryId` (Guid, FK Device, cascade), `CreatedAt`. Unique (`BlockerPrimaryId`, `BlockedPrimaryId`), index `BlockedPrimaryId`. |
| S2 | `PUT /blocks/{deviceId}` (auth, "api" limiter): blocker = identity of the caller, blocked = identity of `{deviceId}`. 404 `unknown_device`; 400 `cannot_block_self` for the same identity; 400 `block_limit` above 1000 blocks per identity; otherwise 204, idempotent. Runs D3. |
| S3 | `DELETE /blocks/{deviceId}`: removes the block of the caller's identity against the identity of `{deviceId}`, 204, idempotent (also for an unknown device). |
| S4 | `GET /blocks`: `{"blocks":[{"deviceId","userHandle","displayName","isBot","createdAt"}]}`, newest first; `deviceId` is the blocked identity (primary). |
| S5 | Enforcement per D2 in `MessengerHub.Blocks.cs`, hooked into the three send cores (`SendReliableMessageCore`, `SendReliableGroupMessageCore`, `FanoutAsync`), so every public variant drops the copies: `SendMessage`, `SendReliableMessage`, `SendGroupMessage`, `SendReliableGroupMessage`, `SendReliableDirectFanout`, `SendReliableGroupFanout` and their `*Silent` twins. `CallSignal` / `BusinessCallSignal` drop every signal type (no pending call, no push); `TypingIndicator` skips the blocker's devices. A send without any block pays one indexed query (`UserBlocks` by `BlockedPrimaryId`). |
| S6 | Entity `UserReport` (table `UserReports`): `Id`, `ReporterDeviceId`, `ReportedPrimaryId`, `ReportedHandle` (snapshot), `GroupId?`, `Category`, `Reason`, `EvidenceJson` (text), `ContactEmail?`, `GoodFaith`, `Status` (`open`/`dismissed`/`actioned`), `CreatedAt`, `ResolvedAt?`. Index (`Status`, `CreatedAt`), index (`ReporterDeviceId`, `CreatedAt`). No FK: a report outlives both devices. |
| S7 | `POST /users/{deviceId}/report` (auth): body `{"category","reason","contactEmail"?,"goodFaith"?,"groupId"?,"messages"?:[{"messageId"?,"sentAt"?,"text"}]}`. Rules: unknown device 404 `unknown_device`; own identity 400 `cannot_report_self`; category as channels (missing = `terms`), else 400 `invalid_category`; reason 1..1000 chars after trim, else 400 `invalid_reason`; contact e-mail max 254 with an `@`, else 400 `invalid_contact`; `illegal` without `goodFaith:true` 400 `good_faith_required`; at most 20 messages, each text 1..4000 chars, else 400 `invalid_evidence`; more than `Moderation:MaxUserReportsPerDay` (default 10) reports by the caller's identity in 24 h 429 `report_limit_reached`. Success 200 `{"reportId","createdAt"}`. |
| S8 | Operator: `GET /admin/user-reports?status=open|dismissed|actioned|all&before=<createdAt>&limit=1..100` (operator auth as the other `/admin` routes) returns `{"items":[{"reportId","reportedDeviceId","reportedHandle","reportedDisplayName","reportedExists","groupId","category","reason","messages","contactEmail","goodFaith","status","createdAt","resolvedAt","reportsAgainstSameUser"}]}`, newest first; never the reporter. `PUT /admin/user-reports/{id}/status` `{"status":"dismissed"|"actioned"}` 204, 400 `invalid_status`, 404. |
| S9 | `DELETE /devices/{id}?includeCompanions=true`: when the caller is a primary, every companion in its server-side device list is deleted with the same cleanup as the caller. Without the parameter nothing changes for old clients. A companion that is an organization auditor makes the whole call 409 `device_is_auditor` before anything is deleted. |
| S10 | Device deletion also removes the device's blocks (both directions, by cascade) and clears `ContactEmail` on the channel and user reports the device filed (the report stays as a moderation record without a way to reach the person). |
| S11 | `GET /devices/{id}/export` (self only, else 403; 404 when gone): the device-scope export: device, its device list, group memberships, mutes, blocks, user reports filed, channel reports filed, channels followed and administered, media metadata, queued message count. `GET /accounts/{id}/export` adds `groups`, `mutes`, `blocks` and `userReportsFiled` (additive keys). |
| S12 | `MessageCleanupService` also deletes user reports older than `Moderation:UserReportRetentionDays` (default 180). |
| S13 | Migration `AddUserBlocksAndReports` (additive: two new tables). Old clients keep working: they never call the new routes, and their sends are filtered like everyone else's. |

## Compatibility

| Client | Behaviour |
|--------|-----------|
| Old app, sender | Its sends to a blocker are dropped silently (same ack). |
| Old app, recipient | Cannot block or report users; unaffected otherwise. |
| Bots | Can be blocked and reported; `calltype_bot` needs no change. |
| Old delete flow (`DELETE /devices/{id}` without parameter) | Unchanged, plus S10. |

## Limits (honest)

- A block is enforced by the server: a hostile server operator could ignore it (it could also read metadata anyway); content stays E2E.
- Evidence in a user report is what the reporter's app says the messages were; the server cannot verify it against ciphertext.
- Account deletion cannot reach copies other people already have on their devices.
- Encrypted backups and media are deleted best effort after the database commit; a storage failure is logged for manual removal.

## Acceptance

1. Server: a blocked identity's 1:1, group and fan-out sends to the blocker are not queued and not pushed; the sender's call completes without error.
2. Server: a blocked identity's call offer to an online and to an offline blocker is not relayed and not pushed.
3. Server: blocking removes queued messages from the blocked identity; unblocking lets new messages through.
4. Server: blocks cannot target self; `GET /blocks` lists the blocked identity with its handle.
5. Server: user report validation, rate limit, operator list without reporter, status update, retention cleanup.
6. Server: `DELETE /devices/{id}?includeCompanions=true` deletes companions; device deletion removes blocks and clears report contact e-mails.
7. Server: device export and the extended account export.
8. App: delete account flow (anonymous and registered) calls the endpoints in order and ends on onboarding with an empty database.
9. App: export saves the JSON through the injected saver.
10. App: block / unblock / report from 1:1 menu, member menu and message menu; blocked chats hidden; blocked users screen.
11. App: legal links open the cs/en pages; onboarding shows the consent line.
12. Web: all eight pages exist, link to each other, carry the footer; `/legal/*` and `/.well-known/*` are excluded from the fallback.
13. Manual checks in `docs/acceptance/go-live.md` (NOT_RUN until done on devices).
