# Bot media: files for every bot, images for llm_bridge

Status: implemented on `feat/bot-media` (based on `release/2026-11-10`, not released).
Owner (2026-11-10): "Jay (i bot) by měl umět poslat obrázek. Codex bot píše, že to neumí. Proč?"

## Today (release/2026-11-10 359295c)
- `calltype_bot` handles text only. A media message (`type: text` + `media` object, spec 2026-11-07-encrypted-media)
  reaches a bot as its fallback body ("Image (12 KB). Update Jay to see it."); inline `type: file` photos are acked
  and ignored. No bot can send a file.
- Media support for bots exists only on the unmerged `fix/bridge-media` (7 commits on 3628fcc, before the client
  protocol split); the running HermesBot is built from it.
- The media format (`MediaCipher`, `MediaInfo`) lives in the app (`calltype/lib/features/media`), not in a package.
- llm_bridge is text only, for all four providers.

## Decisions

| # | Decision |
|---|---|
| M1 | Bring `fix/bridge-media` in with a **merge** (not cherry-picks): its 7 commits keep their ids, so the branch shows as merged and the running HermesBot build maps to history. Conflicts with bot-access (calltype_bot inbound policy, `BotTalkPolicy`, pre-key top-up, hermes_bridge policy publishing) are resolved in the merge commit keeping both sides; the port to the current package layout is a separate commit. |
| M2 | The media format moves to **`calltype_protocol/lib/media/`** (`media_crypto.dart`, `media_info.dart`), not `calltype_core` as on the old branch: it is a wire codec + crypto with no deps beyond `cryptography`, which is the protocol package's job (layering rule: protocol <- core <- app/bots). One copy only: `calltype_core/lib/media/*.dart` re-export it at the old paths (like the other moved protocol files), so the app's `features/media` re-exports (which keep the localized texts) and the bots' `package:calltype_core/media/...` imports stay unchanged. |
| M3 | hermes_bridge behaviour of `fix/bridge-media` unchanged: voice transcripts (ElevenLabs STT), images as `image_url` parts, other files saved and passed as a path, file/voice replies (`MEDIA:`, `[file:]`, `[voice:]`), `POST /send` with files. Only owners' files are downloaded (a peer bot's file stays metadata). |
| M4 | llm_bridge **receives images** from senders it would answer anyway (bot-access rules decide FIRST, nothing is downloaded for an ignored sender; in groups the runtime still requires a mention or reply, so an image needs a caption with `@bot` or a reply to the bot). Accepted: encrypted media of kind image and inline `type: file` photos (`receiveFiles: true`), `image/jpeg`, `image/png`, `image/gif`, `image/webp`, up to **5 MB** (`LLM_IMAGE_MAX_BYTES`, max 20 MB), no downscaling. The type is taken from the file's magic bytes (a wrong declared MIME would make the API refuse). |
| M5 | Per provider: `anthropic` = `image` content block (`source.type: base64`, `media_type`); `openai` = `image_url` part with a `data:` URL; `codex-cli` = `codex exec --image=<file>` with the image written into the bot's CLI work dir (inside the sandbox bind) and deleted after the run; `claude-cli` = `--input-format stream-json --output-format stream-json --verbose`, one user message with text + `image` block (verified live with Claude Code 2.1.319 in print mode: a red PNG answered "Red"; the docs do not list it explicitly). Text-only turns keep the old invocation. |
| M6 | Other files (voice, video, audio, documents, an image over the cap or of another type, an expired download): no model call, a polite reply saying what the bot reads ("I can read text and images (JPEG, PNG, GIF, WebP up to 5 MB)..."). |
| M7 | History never stores bytes: the user turn is saved as `[image: <name>]` + caption. Only the current turn carries the image to the provider; a failed answer stores nothing (as before). |
| M8 | llm_bridge **sends images** only with opt-in `LLM_IMAGE_MODEL` (e.g. `gpt-image-1`), only for `LLM_PROVIDER=openai` (config error otherwise; Codex/Claude CLIs and the Anthropic API cannot generate images). The system prompt then gets a hint: a line `[[image: <prompt>]]` in the answer makes the bridge call `POST {OPENAI_BASE_URL}/images/generations` (`n: 1`, `size: 1024x1024`, `b64_json`), write the PNG to the work dir, send it with `calltype_bot` `replyFile`, delete it. At most 2 images per answer; the tag is removed from the text; a failed generation adds a short note instead. History keeps `[image sent: <prompt>]`. Without `LLM_IMAGE_MODEL` the tags are left as text and no image API is called. |
| M9 | Default system prompt says the bot can see images the user sends. |
| M10 | No server, app UI or wire format change. Old apps see what they saw before (fallback text for media from bots). |

## Compatibility
| Peer | Effect |
|---|---|

| Old bot build (text only) | unchanged, acks media as text |
| Server | unchanged |

## Implementation notes

- M1: merge commit `merge: fix/bridge-media into feat/bot-media`; conflicts only in calltype_bot (exports, `BotMessage.poll` + `attachment`, type dispatch keeps `pin`/`poll-vote` ignored), its README and test helpers, and hermes_bridge `runBridge` parameters (`inbound` + media options). No behaviour of either side was dropped.
- M5: Codex takes `--image=<file>` (with `=`; `-i <FILE>...` is multi-valued). Both CLI paths were run live on this host through the provider classes with a red test PNG (Claude Code 2.1.319: "Red.", codex-cli 0.167.0: "Red"); the temp file was gone afterwards.
- M8: a turn whose answer is only tags shows `[image sent: <prompt>]` as its text, so a progress message never stays at "Working on it...". Small generated images (<= 256 KiB) go inline like the app's photos; 1024x1024 PNGs usually take the media path.
- `/help` mentions pictures.
