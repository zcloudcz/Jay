# calltype_bot

Headless CallType (Jay) bot runtime. A bot is an ordinary E2E device — own
`CT-XXXX-XXXX` handle, own keys — built on the same `calltype_core` protocol
code as the app. The server stays an opaque relay; the plaintext is visible to
whoever runs the bot, like for any other peer. Pure Dart, no Flutter SDK.

```dart
final bot = await CallTypeBot.start(
  apiBaseUrl: 'https://…',
  storePath: '/data/bot.store',   // + /data/bot.store.sqlite next to it
  displayName: 'Hermes',          // BOT_STORE_KEY is read from the environment
);
print(bot.handle);                // handle + ct:// invite are also logged on first start
await bot.onMessage(
  (msg) async => msg.reply('you said: ${msg.text}'),
  allowSender: (deviceId) => true, // optional; checked BEFORE decryption
);
```

`onMessage` connects. It is deliberately the step that goes online: the server
pushes everything queued the moment a device connects.

### Starting a message and reading group settings

```dart
await bot.send(to: 'CT-XXXX-XXXX', text: 'nightly build is green'); // 1:1, all the user's devices
await bot.send(to: groupId, text: 'deploy 28f5070');               // group the bot is in

final info = await bot.group(groupId);
info.botTalk.mode;            // BotTalkMode.off / all / selected (old server: off)
info.botTalk.maxBotTurns;     // + allowedBotDeviceIds, pauseMinutes
info.member(id)?.isAdmin;     // members: deviceId, role, handle, isBot
```

- `send` uses the same encryption and fan-out as `reply`; it needs the hub
  connection (call `onMessage` first). Unknown handle or a group the bot is not
  in throws `BotSendException`. WHO may be messaged is the caller's policy.
- `group` is cached and re-read on the hub's `GroupChanged` hint, on
  `DeviceListChanged`, when a group message comes from a sender the cached list
  does not know, and at the latest after `groupCacheTtl` (default 5 minutes).
- `BotMessage.groupId` (null for 1:1) and `BotMessage.senderIsBot` (from the
  group's member list; null when unknown, e.g. 1:1).
- `onMessage(..., allowGroupSender: (senderId, groupId) async => ...)` is a
  second pre-decrypt chance for a sender `allowSender` refused when the server
  routes the message to a group, so a bot can admit other bots of a group by
  its settings (one cached group lookup) instead of a static list.

### Posting to a channel

```dart
final postId = await bot.postToChannel('CH-XXXX-XXXX', 'Weekly digest ...'); // or the channel id
```

- The channel owner must first make the bot a **publisher** (app: channel
  profile -> Admins -> add by handle -> role Publisher). The server is the only
  authority: role, moderation suspension and the daily bot limit
  (`Channels:MaxBotPostsPerDay`, default 20 per channel per 24 h).
- One public `text` post (no E2E: channels are public), labelled BOT in the app.
  At most `channelPostMaxChars` (4096) characters; longer or blank text throws
  `ArgumentError` instead of being split, because every post counts against
  the limit. The post id is generated by the bot, so a retry after a lost
  response is idempotent on the server.
- Refusals throw `BotSendException` with `statusCode` and the server `code`:
  403 `channel_suspended` (`channelSuspendedCode`), 403 without a code (not
  owner/admin/publisher), 404 unknown channel, 429 `bot_post_limit`
  (`botPostLimitCode`). Network errors and 5xx are rethrown unchanged.
- Needs no hub connection (no `onMessage` first).

### Agent messaging: replies, buttons, edits, commands

```dart
// Buttons (max 8; id 1..64 of [A-Za-z0-9_.:-], label 1..40 chars).
final sent = await msg.reply('Delete 3 files?', actions: const [
  MessageButton(id: 'yes', label: 'Yes'),
  MessageButton(id: 'no', label: 'No'),
]);
await sent.edit('Deleting...');                       // null = keep the buttons
await sent.edit('Deleted 3 files.', actions: const []); // [] = remove them

// Presses on this bot's own button messages, OUTSIDE the conversation queue.
bot.onAction((press) async {
  press.action!.id;        // 'yes'
  press.action!.messageId; // sent.id
});

await bot.setCommands(const [BotCommand(command: 'help', description: 'Show help')]);
bot.deepLink(start: 'invite_42'); // calltype://bot/CT-XXXX-XXXX?start=invite_42
```

- `BotMessage.replyTo` (`id`, `senderId`, `preview`), `mentions` (structured
  identity ids), `action` (a button press), `mentionsBot` (structured mention or
  `@handle` text), `repliesToBot`, `addressed` (= either).
- In a group a `reply` quotes the message it answers (`replyTo`, first 100
  characters); 1:1 replies do not quote. `send` and `reply` return a
  `BotSentMessage` that can be `edit`ed (wire `type: edit`, `editOf`).
- A press on a message the bot sent with buttons goes to `onAction` when set,
  even while that conversation's handler is still running (WHY: that handler
  may be waiting for exactly this press, e.g. an approval). Ids of button
  messages are kept in memory and in the DB (`backupState`
  `sent-actions:<id>`), so a press after a restart is still recognised.
  Without `onAction` presses reach the normal handler (body = button label).
- Edits from others are acknowledged and ignored (the bot keeps no history).

### Reactions

```dart
bot.onReaction((r) async {          // set before onMessage
  if (r.removed || !r.targetIsOwn) return;
  print('${r.senderId} reacted ${r.emoji} to "${r.targetText}"');
});
```

- `type: reaction` messages (spec
  `docs/superpowers/specs/2026-11-07-message-reactions.md`). Without a handler
  they are acknowledged and ignored, like every non-text type before.
- 1:1: every valid reaction. Group: only reactions to the bot's own messages.
- `targetText` is the first 200 characters of the bot's message: while a
  handler is set the runtime remembers the start of the last 500 messages it
  sent (`sent-text:` rows in the local store, updated by `edit`).
- Runs in the conversation's queue, no typing indicator, acked after the
  handler; a failing handler is only logged (no apology message).

## What the runtime guarantees

- **Registration** with `isBot: true` on first start; identity is reused afterwards.
- **Sessions** are established from the first incoming pre-key message.
- **At-most-once handling.** The message UUID is committed to SQLite in the same
  transaction as the ratchet advance. A replay (lost ack, reconnect, restart,
  crash mid-handler) is acknowledged but never reaches the handler again.
- **Ack after the handler finished**, typing indicator while it runs.
- **Groups:** the handler runs only when the bot is addressed: a structured
  mention, the text `@<handle>` / `@<display name>`, or a reply to one of the
  bot's messages. Replies use the per-member fan-out like the app.
- **Ordering:** handlers run serially per conversation, concurrently across conversations.
- **Handler exception** → logged, short apology sent, loop continues.
- **Reconnect forever** (the app gives up after four attempts; a bot has no user to tap retry).
- **Dead-session watchdog.** A connection can stay TCP-ESTABLISHED, and even keep
  answering WebSocket pings (a proxy in front of the API does), after the hub
  behind it is gone. The transport counts any frame from the server; after
  `hubServerTimeout` (default 60 s, the server pings every 15 s) without one it
  logs `Hub: nothing from the server ...`, drops the socket without waiting
  for its close handshake and reconnects. Hub invocations fail after 2 min
  without a completion and HTTP calls have timeouts, so the serial receive
  queue can never wait forever.

## Storage and its limits

| File | Content | Protection |
| --- | --- | --- |
| `<storePath>` | identity keys, pre-keys, device secret | AES-256-GCM, key = `BOT_STORE_KEY` (base64, exactly 32 bytes; `openssl rand -base64 32`), atomic temp-file + rename |
| `<storePath>.sqlite` | Double Ratchet sessions, pinned peer identities, seen message ids | **plaintext on disk — exactly like the app's drift DB today** |

So `BOT_STORE_KEY` protects the long-term identity, **not** the session state:
the host running the bot must be trusted. Message bodies are not stored.
Losing the store = a new bot identity (contacts see a different device).
A wrong key refuses to start rather than silently creating a new identity.

## Known gaps (protocol, not runtime)

- **No one-time pre-key replenishment:** the server has no endpoint to upload
  more (the app cannot either). After the initial 100 are consumed, new
  sessions fall back to X3DH without a one-time key, which the protocol supports.
- Text only; attachments and calls are ignored (acknowledged, not handled).

## Tests

`dart test` — no Docker. The runtime tests use two real crypto stacks (a fake
user on the real `SessionManager` ↔ the bot) over a fake hub transport and a
loopback REST fake. A test against the real API is not included: it needs PostgreSQL.

Generate the core's drift code first:
`cd ../../client/calltype_core && dart pub get && dart run build_runner build --delete-conflicting-outputs`.
